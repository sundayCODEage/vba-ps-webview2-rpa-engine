### 1. 開発背景と概要 (Overview)
セキュリティポリシー等によりブラウザの開発者ツール（F12）が利用できない業務端末環境において、画面上の操作対象要素のセレクタや座標を特定するために開発した要素ピッカー（ Lib-DevTools_v303.ps1 / Mod_TestDevTools.bas ）の検証記録です。<br>
<sub>（職場のPC環境では F12 開発者ツールが使えません。ページソースを見たり、デバッグ・証跡モジュールで画面内の操作可能要素を取得したりと地道な作業をしています。業務システムのRPAでは一度セレクタを特定できれば良いため開発時間との兼ね合いになりますが、補助ツールとして活用できます。）</sub><br>

本モジュールは、OSレベルの **UIAutomation (UIA)** とブラウザ内部の **JavaScript / Chrome DevTools Protocol (CDP)** を連携させ、マウスポインタの位置から同一オリジンの多段iframeやShadow DOMを透過してCSSセレクタ（またはXPath）および座標情報（ BoundingBox ）を取得します。

| 項目 | 内容 |
| :--- | :--- |
| ① Shadow DOM内のセレクタ生成と安定性テスト | el.getRootNode()（ShadowRoot基準）で一意性を判定。IDやクラスがない要素でも DOMUtils.generateCssSelector で階層CSSセレクタを生成し、deepQuerySelector で安定性テストまで一貫して動作。 |
| ② 同一オリジンiframe内の座標算出 (I列・J列) | getAbsoluteBoundingBox により、親フレーム（win.frameElement）の枠オフセットを window.top まで再帰的に加算し、トップ画面基準の絶対座標を算出。 |
| ③ 透過・隠蔽UI（モダンUI）の判別 | isSubstitutable 関数を追加し、すり替え候補が実際に可視サイズ（width > 0, height > 0, opacity > 0.01）を持つか検証。隠蔽時は表示されている装飾要素（span 等）を捕捉。 |
| ④ リアルタイム・ホバーハイライト | マウス移動（mousemove）に追従し、Shadow DOMや同一オリジンiframe内部の要素も赤枠でリアルタイムに表示。 |
| ⑤ ピッカー取得時の通信負荷と応答速度 | PointReverse 優先時は事前のスナップショット取得を省略（オンデマンド化）。UIA照合時も layout.bounds 配列から座標を一括展開することで、応答時間を約1秒に短縮。 |

### 3. 主要機能と内部仕様 (Key Mechanisms)
#### 3.1 透過・隠蔽UIの判別 (isSubstitutable)
Bootstrap等のモダンUIでは、本来の `<input type="radio">` 等を opacity: 0; width: 0; height: 0; で非表示にし、隣接する `<span>` タグ等で外観を描画する実装が多く見られます。<br>
ピッカーの座標逆引き（Get-CorePointReverseJs）では、LABEL や SPAN から内部・隣接の input へ対象をすり替える際、isSubstitutable 関数によって「その input が実際に可視サイズを持っているか」を判定します。隠蔽されている場合はすり替えを行わず、画面上でクリック可能な装飾要素（例: T04 の span.modern-radio-label）を捕捉します。

#### 3.2 オンデマンドDOMSnapshotと layout.bounds の活用
* **PointReverse 優先時のスナップショット省略:** UsePointReverse が有効な場合、事前の全件DOMスナップショット取得をスキップし、ブラウザ内の elementsFromPoint で直接要素を特定します。これによりピッカーの応答時間を約1秒に短縮しています。
* **UIA照合・Fuzzy検索時の layout.bounds 統合:** ルートB（UIA照合・Fuzzy検索）を使用する場合は、DOMSnapshot.captureSnapshot が返すフラット配列内のテキストノード（nodeType = 3）とレイアウト境界配列（layout.bounds）を Convert-DomSnapshotFlat 内で各ノードへ直接結合し、個別の DOM.getBoxModel 通信を最小限に抑えています。

#### 3.3 同一オリジンiframeの座標補正と視覚フィードバック
標準の getBoundingClientRect() は、要素が属するドキュメント（iframeの内部枠）の左上を起点 (0, 0) とした相対座標を返します。<br>
getAbsoluteBoundingBox 関数は、対象要素が同一オリジンのiframe内部にある場合、win.frameElement.getBoundingClientRect() のオフセットをトップウィンドウ（window.top）に到達するまで再帰的に加算します。これにより、同一オリジンiframe内要素（T22, T23）でもトップ画面基準の絶対論理座標が算出されます。<br>
あわせて、iframe内要素を取得した際は背景色を薄黄色（#ffffcc）に2秒間変化させ、ExcelシートのK列に *Frame要素 と記録して注意喚起を行います（クロスオリジンiframe等でアクセス制限がある場合は相対座標となります）。

### 4. OS・ブラウザ間の座標変換式 (Coordinate Conversion)
#### 4.1 Excelシート I列・J列（補正X, 補正Y）の算出ステップ
WriteMappingToExcel では、取得した BoundingBox（ページ絶対論理座標）から以下の計算式でブラウザ左上起点の物理Client座標を算出し、I列・J列へ出力します。
1. **STEP 1 (対象取得):** ピッカーで対象要素の boundingBox（x, y, width, height）を取得します。
2. **STEP 2 (中心算出):** 要素の左上座標に幅・高さの半分を加算し、要素の中心論理座標を求めます。
3. **STEP 3 (DPR乗算):** 中心論理座標にディスプレイのDPR（例: 1.25）を掛け、物理Client座標（Client X, Client Y）に変換します。

```text
【計算例：T12 (Wikipedia 検索ボタン) / DPR = 1.25 の場合】
  * 要素の論理座標 (BoundingBox): x = 729, y = 17, width = 52, height = 32
  * 中心論理座標: X = 729 + (52 / 2) = 755 / Y = 17 + (32 / 2) = 33
  * 物理Client座標 (I列・J列):
      I列 (Client X) = CLng(755 * 1.25) = 943.75 → 944
      J列 (Client Y) = CLng( 33 * 1.25) =  41.25 →  41
```

### 5. 物理フォールバックと Robust DOM の検証 (T31〜T33)
* **JavaScriptによるイベント発火を受け付けないUI:**
ボット対策や独自のイベント制御により、JSの element.click() を無視し、OSレベルのマウスクリックやキー入力のみを受け付ける画面です。<br>
👉 Invoke-DesktopCoordinateClick を使用します。
* **フレームワークの内部ステート更新:**
element.value の書き換えだけでは内部状態が更新されない特殊な入力コンポーネントです。<br>
👉 座標を物理クリックしてフォーカスを当て、Invoke-DesktopSendKeys でキー入力を行います。
* **DOM要素として分割されていない領域:**
`<canvas>` 要素（グラフ・描画ツール）や地図コンポーネントなどです。<br>
👉 座標を指定してクリックします。

#### 5.1 テスト1 & 2： 物理操作へのフォールバック (T31(物理Input) / T32(物理Click))
自動テストの T31 および T32 では、Test-WebPointReverse で取得した boundingBox のJSON文字列を保持した上で、存在しないセレクタ（#not_exist_...）を Set-WebTextInput と Invoke-WebClick に渡してDOM探索を意図的に失敗させます。

```vba
                    "Selector", fakeSelector, "Value", "Fallback OK!", "BoundingBox", bboxJson, "TimeoutSec", 2))
Else

End If
```
